## 1. Первопричина утечки соединения (явление A) — НЕ устранена, локализована

### 1.1. Установленный факт

В одном процессе тестов соединение, открытое внутри
`test_async_asend_resets_cache`, остаётся незакрытым до выхода процесса.
Сигнатура (pg_stat_activity): `state=idle`,
`last_query='SELECT "blog_invalidationepoch"."id", "blog_invalidationepoch"."epoch" …'`
— это `InvalidationEpoch.get_epoch()`, вызываемый из `get_blog_cache_epoch()`.

### 1.2. Точная точка (трасса NEWCONN/CLOSE, `tools/trace_connections.py`)

Лог `logs/threads-trace.log` (квартет на `main@22926cee`):

```
23:09:27.969255 TEST START test_async_asend_resets_cache
23:09:27.988800 N    pid=566093 thread='MainThread' alias=default   ← чтение эпохи №1
23:09:28.014675 LEAK pid=566094 thread='MainThread' alias=default   ← утечка: открыта ВНУТРИ теста
23:09:28.021863 TEST END   test_async_asend_resets_cache
23:09:28.561565 C    pid=566093 thread='MainThread' alias=default   ← соединение №1 закрыто позже
```

Два соединения алиаса `default` в MainThread живы одновременно
(566093 + 566094) — закрытие первого просходит только при следующем
переоткрытии. Соединение-утечка 566094 не закрывается никаким штатным
путём вплоть до выхода процесса (после выхода процесса pg_stat_activity
пуст — факт замера).

### 1.3. Механика внутри теста (пробел А из ревью координатора)

`test_async_asend_resets_cache` (blog/tests_epoch.py):

- ORM-вызовы выполняются внутри `asyncio.run(scenario())` при
  `DJANGO_ALLOW_ASYNC_UNSAFE=true` — защита Django обходится;
- `await request_started.asend()` выполняет sync-приёмники
  (`_reset_epoch_cache`, `close_old_connections`) в потоке-исполнителе
  asgiref;
- возвращаемое `after_signal = _epoch_var.get()` **не проверяется**;
- итоговое чтение свежей эпохи происходит **после ручного**
  `_reset_epoch_cache()` — тест проходит независимо от того, что сделал
  сигнал с ContextVar.

Вывод: тест не проверяет действие сигнала в async-контексте и сам создаёт
комбинацию (ORM в async + asend + CONN_MAX_AGE=0), в которой наблюдается
утечка. Гипотеза механизма: переоткрытие соединения внутри async-контекста
после `close_old_connections` (CONN_MAX_AGE=0 закрывает соединение по
сигналу) ускользает от путей закрытия Django — требует разбора на уровне
Django/asgiref. **Расследование не завершено и не входит в текущую задачу.**

## 2. Граница `application_name` (пробел Б) — метка, а не удостоверение

- Метка `vs-wagtail-tests-<pid>-<hex8>` уникальна для запуска и защищает от
  случайного совпадения, но PostgreSQL не проверяет, кто отправил метку:
  клиент может указать чужую метку намеренно.
- Для локального доверенного окружения — достаточный практический механизм.
  Для строгой модели «чужую сессию нельзя завершить даже при имитации» —
  недостаточно. Требуется фиксация модели угроз до усложнения архитектуры.
- **Факт серверной метки подтверждён**: `logs/label-capture.log` — 18 сессий
  прогона, все с `application_name='vs-wagtail-tests-565391-5a203f24'`
  (монитор `tools/label_monitor.py`).

## 4. Дефекты раннера, найденные координатором (подтверждены инспекцией)

На `main@22926cee`, `vsproject/test_runner.py`:

1. **Отчёт дренажа неполон**: `_drain_test_db` при таймауте печатает
   WARNING «own sessions still present», но не возвращает выжившие
   собственные pid'ы отдельным полем; `_drain_and_clear` проверяет только
   `report["foreign"]` и печатает «drained … DROP без гонки» даже при
   живых собственных сессиях. Демонстрация: `logs/drain-report-gap-demo.log`
   (инструмент `tools/demo_drain_report_gap.py`, имитация отказа
   terminate) — сообщение «DROP без гонки» напечатано при живой сессии.
2. **Результат `pg_terminate_backend()` не проверяется**: тот же лог —
   pid попал в `terminated` при живой сессии.
3. **Метка назначается всем настроенным алиасам**, а не только
   используемым текущим набором (labeling инертен, но область стоит
   сузить; ограничение — labeling должен предшествовать открытию
   соединений, а old_config известен только после setup).

Все три — предмет отдельного исправляющего PR к раннеру (не входят в
досье-ветку).

## 5. Явление B (гонка close→DROP)

Зафиксировано в логах: ObjectInUse при пустой диагностике
(`logs/parallel-run-B.log` попытки до дренажа: recreate-блок
«1 other session» при отсутствии сессий в последующем снимке). Дренаж
(закрыть → дождаться нуля сессий → terminate только свои) устраняет гонку
практически: `logs/quartet-*.log` — 15/15 exit=0,
`logs/full-suite-*.log` — 2/2 exit=0.
